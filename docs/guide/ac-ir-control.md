# 用 ESP32 红外控制空调（海信/美的/格力/海尔通用）

国产成品空调（海信等）是"云锁定"的——它的 WiFi 模块只连厂商云，没法直连你的 MQTT。
本方案绕开这层，用一个 **ESP32 + 红外发射管**假装成空调遥控器：Home Guardian 把
"开机/制冷/26℃/自动风"这样的完整状态经 MQTT 下发给 ESP32，ESP32 合成对应品牌的
红外帧发射出去。

- ✅ 完全复用现有 MQTT 架构，本地控制，无厂商云依赖
- ✅ 不挑品牌——换空调只改一个协议常量
- ⚠️ 红外是**开环**（只发不收）：发完不保证空调真执行了，也读不到空调真实温度。
  强烈建议同一块 ESP32 再接一个 DHT11，用真实室温做闭环展示与自动化。

---

## 一、准备硬件

| 器件 | 说明 |
|---|---|
| ESP32 开发板 | 任意 esp32dev |
| 红外发射管（940nm） | 淘宝几毛钱一个 |
| NPN 三极管（如 S8050）+ 100Ω/1kΩ 电阻 | **必须**，勿把红外管直连 GPIO——电流不够射程只有几厘米 |
| DHT11/DHT22（可选，强烈建议） | 做闭环用，测真实室温 |

**红外发射驱动电路**（射程可达数米）：

```
ESP32 GPIO25 ──[1kΩ]── B (三极管基极)
3V3 ──[100Ω]── 红外管(+) ── 红外管(-) ── C (集电极)
                                          E (发射极) ── GND
```

把红外管**对准空调的接收窗**（一般在室内机显示屏附近）。

## 二、按原遥控器匹配协议和型号

固件 1.2.0 和配套后端提供 65 种空调协议：IRremoteESP8266 2.9.0 的 64 种通用状态协议，
以及独立驱动接入的 `KELON168`。清单唯一来源为 `resources/ac-ir-protocols.json`，
`python scripts/generate-ir-catalog.py` 生成固件目录，`--check` 校验是否同步。
协议数量不等于品牌数量，也不代表每个型号、每项功能都经过实机验证。
库虽将 YORK 列为支持，但该版本通用接口缺少实际发送分支；编码回归发现后已从选项中排除。

海信/科龙 RCH-R0Y3 系列优先验证 `KELON168`，库将其列在 DG11R201 兼容型号下；
`RCH-ROY3-2` 的后缀变体仍需实机验证。不要仅凭海信品牌选择 COOLIX/HITACHI，
`KELON`（48位）和 `KELON168`（168位）也不能互换。
新增选项还包括海尔/日立/大金/三菱的多个变体及 LG、夏普、东芝等。

格力、松下、富士通、LG 等协议有多个遥控器型号。在设备详情中先选择协议，再选择
该协议提供的型号；自动化编辑器也会联动。切换协议重置为默认型号，保持温度和电源等期望值。
选定协议/型号后，固件存入 NVS，重启沿用；无效输入返回明确失败，不会退回旧协议却显示成功。

精确识别可接红外接收头（如 VS1838B → GPIO14），使用库的 `IRrecvDumpV3`，
对原遥控器开/关、调温、切模式和扫风分别抓码，记录 `Protocol:`、位数及型号。

### 升级顺序

1. 部署后端代码，运行 `php webman migrate:run`，更新空调模板与已有红外设备的控制选项；自定义其他控制点保留。
2. 使用新的 `firmware/src` 和 `firmware/include` 重新编译并刷入网关，保留自身配置与接线。只升级服务器不能升级 ESP32。
3. 更新 H5/小程序客户端，刷新设备详情，选择协议和型号后验证。

旧网关固件不支持这些新增协议。示例 `config.h` 默认不挂载红外，需通过模块管理添加，
或在首次空清单启动前设置 `AC_IR_ENABLED=1`。已有 NVS 清单不会因重烧配置自动改引脚。
串口 `[AC-IR] ready`、`[AC-IR] tx` 会打印实际协议、型号与引脚。
回退应用代码时迁移不删除扩展选项，避免丢失用户选择；数据结构保持兼容。

## 三、装上红外模块

### 方式 A：设备已经在跑 —— 直接热插拔，免烧录（推荐）

网关挂载了哪些模块由运行期清单决定，所以已上线的设备**不用重新烧录、也不用恢复出厂**：

1. App →**设备管理**→ 点开你的**网关**→「**子设备**」；
2. 模块类型选「**红外空调**」，GPIO 填你接红外管的脚（默认 25），起个名；
3. 「插入并同步」。

固件会实例化红外驱动、存进 NVS 清单并上报，平台随即建出一台 `type=ac` 的子设备。
掉电重启沿用，不必再动。

> GPIO34-39 是**仅输入**引脚，驱动不了红外管，选中会被拒绝。

### 方式 B：全新设备首次烧录

`config.h` 里的开关只用于**首次开机播种默认清单**（此后以 NVS 为准）：

```cpp
#define AC_IR_ENABLED   1                        // 首次开机默认挂一个红外空调模块
#define IR_LED_PIN      25                       // 你接红外管的 GPIO
#define AC_PROTOCOL     decode_type_t::COOLIX    // 首次开机默认协议，之后可在 App 里切
```

`platformio.ini` 已包含 `crankyoldgit/IRremoteESP8266` 依赖，直接编译烧录：

```bash
cd firmware && pio run -t upload && pio device monitor
```

WiFi/MQTT 凭证走两种方式（与传感器一致）：
- **自助配网**（默认）：WiFi、MQTT 凭证与平台地址留空，没有已保存 WiFi 时进入 SoftAP；在 App 生成配对码，复制平台地址到设备配网页，自注册获取 MQTT 凭证；
- **手动烧录**：直接把真实 WiFi + 后台建好的设备 uid/密码填进 `config.h`。

## 四、在后台/App 里把它变成"空调"

空调是一台**挂在网关下的独立子设备**（`type=ac`，有自己的在线状态与告警规则）。
它上线后还要套上"空调"能力，这决定 App 上显示什么控件：

1. **App → 设备管理**（或管理后台），找到这台空调子设备；
2. 编辑设备，「**控制能力**」选内置的 **「空调」**（数据库已预置，`device_category=ac`、`control_mode=merge`）；
3. 保存。套模板时**设备类型**会自动对齐为 `ac`，一般无需再手动改。

> ⚠️ 别把**网关本身**的类型从 `gateway` 改掉——平台按 `type='gateway'` 决定网关离线时
> 是否批量下线其下子设备，改了会让子设备一直卡在"在线"。空调是子设备，与网关是两条记录。

现在 App 设备详情页会出现：**电源开关 · 模式(制冷/制热/除湿/送风) · 温度(−/＋ 步进) · 风速 · 扫风 · 红外协议**。关机时其余控件自动置灰；「红外协议」用于第五步逐个试协议。

## 五、验证

1. App 里打开这台空调 → 点"电源"；
2. 看 ESP32 串口应打印 `[CMD] 收到指令: action=set_state` 和红外发射日志；
3. 空调响一声、执行 → 成功。

工作链路：

```
App 改任一项 → 后端 ActuatorService(merge) 合并出完整状态
   → MQTT home/downstream/{空调uid}/command/set {action:set_state, params:{power,mode,temp,fan,swing}}
   → 网关代收（后端 ACL 放行网关订阅其下子设备的 downstream）
   → ESP32 IRac 合成红外帧发射 → 空调
   → ESP32 回 command/reply + 上报 state/post（多端同步显示）
```

**若空调没反应 → 逐个试协议（无需接收器、无需重烧）**：

1. 先把空调控制卡设为 开机 / 制冷 / 25℃；
2. 优先按原遥控器识别结果选择协议；RCH-R0Y3 系列先验证 `KELON168`；
3. 若该协议有多个型号，选择与原遥控器对应的型号。发送成功不代表空调实际接收；
4. 分别验证开关机、温度、风速和扫风。重复调温时不能导致电源、扫风或灯光反复切换。

开发验证：`python scripts/generate-ir-catalog.py --check`、后端 PHPUnit、
`bash tests/Firmware/run.sh`（需 g++ 及锁定版 PlatformIO 库目录）和示例配置 `pio run`。
主机测试使用库的真实编码/发送实现及模拟引脚，校验全部协议接受发送、Kelon168 校验和及波形解码；
它不能验证发射管电流、接线、实际载波精度或空调对特定型号的兼容性。

> 全部试完仍无反应，可能是发射角度/距离/驱动问题（回到第一步查接线），或极少数机型 IRac
> 不支持、需走"原始码学习"（见下）。

## 六、闭环（强烈建议）

红外发完不知道空调真实状态。给这块 ESP32 同时开启 DHT11（`SENSOR_DHT11_ENABLED 1`），
它会作为子传感器上报真实室温湿度。这样你可以：

- App 上看到**空调控制卡 + 真实室温**并排；
- 建**自动化**："室温 > 28℃ → 下发 空调 制冷 24℃"；建**告警规则**："室温持续 5 分钟 > 32℃ 报警"（配合刚上线的双向迟滞防抖，抖动不会刷屏）。

---

## 七、协议不支持时的兜底：原始码学习

极少数机型 IRac 不支持。此时用"录制—回放"：对每个按键（开、关、16℃…30℃、各模式）
用 `IRrecvDumpV3` 抓原始 `rawData[]`，存进固件按 `set_state` 的目标状态回放对应码。
这条路万能但繁琐（每个组合一条码），需要时再单独做一版学习型固件。
