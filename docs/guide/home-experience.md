# 家庭使用体验第一版

本版围绕现有 ESP32 / MQTT 设备实现，未增加米家、Aqara、Zigbee、蓝牙等第三方适配。

## 家庭与首页

- 管理 → 家庭模式：在家 / 离家 / 睡眠。管理员且具备全部房间权限才可切换。切换前显示适用规则，切换本身不发送设备指令，下一次遥测或计划触发时生效。
- 管理 → 房间管理：创建空房间、排序、删除空房间；从现有设备位置初始化房间。同名房间按家庭隔离。设备位置仍兼容旧的文本位置；改名需先调整设备和成员权限。
- 设备详情 → 设为常用：个人收藏，首页置前或只看常用。首页展示当前模式、未处理告警和在线情况；最多展示 100 个有权限的设备。

## 自动化

一条规则由触发、执行限制、动作列表组成：

1. 遥测数值或布尔值（布尔在表单中用 1/0）满足阈值，或计划到期。
2. 触发消息未过期；遥测持续时间 / 冷却间隔已满足，且本次持续满足未执行过。
3. 当前家庭模式、时间窗口及最多 10 个组合条件满足。组合关系为全部满足 / 任一满足，每项单独判断数据有效期。跨午夜窗口如 22:00-07:00；相同起止时间表示全天。
4. 涉及的目标设备未处于人工接管。人工接管时整条规则暂停，通知也不执行。
5. 按顺序提交最多 20 个动作。每个动作独立记录设备回执或通知结果，单个失败不停止其他动作。

当前不是“等待前一动作成功才执行下一动作”的流程编排。对同一设备重复提交动作时，后一条可能因前一条待回执而跳过；建议合并为一次完整状态控制。

保存后可试运行已保存版本，读取当前快照、持续计时、冷却与重触发状态，不发送指令，不创建执行记录，也不更改计时。修改尚未保存时仍检查保存版本。

不适用的家庭模式、时间窗口、组合条件、人工接管，会留下跳过记录及实际条件快照；同一规则该类跳过最多每分钟记录一次。持续时间、冷却、已执行锁属于触发等待，不会每条遥测都新增记录，试运行可查看原因。组合条件变化不会独立触发规则，等待原触发设备下一次上报或计划到期。

缺失、过期、非数字/布尔数据不能满足条件。缓存保存服务器实际接收时间，不再把每次接口查询时间当成数据时间。积压触发消息超过规则有效期不会发送控制；过长的采样间隔会重置持续计时。

## 人工优先与冲突保护

手动控制成功入队前设置 30 分钟接管期。非法参数或排队失败恢复先前的接管设置。详情页可立即恢复自动化或暂停 30 分钟 / 2 小时，后端支持最长 24 小时。自动恢复仍等待原规则下一次有效触发。

控制通过同一个入口：每台设备使用原子 Redis 锁，已有待回执控制时拒绝新控制。第一条已接受请求保持顺序，后一条自动化跳过并记录原因；不会静默覆盖已发指令。人工接管优先于后续自动化，但不能撤销已发出的物理指令。空调自动指令最短间隔 180 秒，人工操作不受该自动间隔限制，仍须等待上一条回执。

本版未实现用户可配置的规则优先级、自动重排和失败重试，避免在不确定实际设备状态时重复物理控制。

## 状态可信度与维护

期望状态、设备上报状态、最近回执分开保存/展示。历史期望行无法可靠重建真实上报，因此新字段从空开始，等待设备再次上报。

红外空调一律标注实际状态未验证。ACK 仅能证明网关发出红外；ESP32 的状态上报也不能证明空调接收或实际开启。首页快捷控制现在等待回执并在失败时回滚。

设备编辑可配置预计上报周期（10-86400 秒）；数据超过周期三倍标记过期。传感器离线扫描使用全局超时与周期三倍的较大值；网关和执行器仍采用全局心跳超时。若设备有 `battery` / `battery_percent` 指标，可按普通指标展示及建低电量规则；本版不编造不存在的电池读数。

## 告警闭环

告警确认表示开始处理；处理备注记录处理人和时间；人工标记解决不等于传感器恢复。实际数据恢复时写入独立 `recovered_at`，界面区分人工处理与传感器恢复。已经解决的记录不会被确认操作重新打开。历史告警无独立恢复记录时显示未记录，不能推断历史原因。

## API

- `GET /api/home/overview`：当前模式、有权限设备状态、房间顺序及未处理告警数。
- `PUT /api/home/mode`：`{mode: "home" | "away" | "sleep"}`。
- `GET /api/rooms`、`PUT /api/rooms`（name、sort_order）、`DELETE /api/rooms/{id}`。
- `PUT /api/devices/{id}/favorite`：`{is_favorite: true}`。
- `PUT /api/devices/{id}/override`：`{minutes: 0}` 恢复，1-1440 暂停。
- `GET /api/automations/{id}/preview`：规则涉及的全部设备都需具备位置权限。
- `PATCH /api/alert-logs/{id}/handling`：`{note: "处理情况"}`。

自动化的 trigger_config 增加 modes、conditions、condition_logic、max_age_sec、time_window；原规则省略新字段时不限模式/窗口/组合条件，数据有效期默认 900 秒。所有组合设备和通知渠道仍必须属于本家庭。备份自动包含新表和字段。

## 后续待办

- 米家等第三方设备：延期，先按具体型号验证协议和真实硬件。
- 网关本地离线自动化：需固件规则同步、执行归属、防重复与离线记录补传。本版仍由服务器执行，服务器不可达时不宣称自动化可用。
- 多家庭创建/切换、临时访客与精细授权：保留家庭隔离和现有成员管理，暂不开放新入口。
- 事件流适配（非状态型重复事件）、规则优先级与等待 ACK 的流程编排、告警升级/指派：后续版本。

## 验证

隔离 Redis / PostgreSQL 容器回归覆盖：模式阻止与恢复、组合条件 ALL/ANY 和过期数据、人工接管/恢复、并发请求与空调间隔、只读试运行及跨家庭/位置隔离、真实状态保留、积压消息不执行、告警人工处理与实际恢复、房间排序和迁移回滚。前端类型检查、既有 7 个回归测试、H5 / 微信构建通过；没有进行真实 ESP32 或空调硬件验收。
